# ADR 0001: Репозиторий и стратегия тестирования для порта kogda-igra на ASP.NET Core

## Статус

Принято

## Контекст

kogda-igra.ru — календарь ролевых игр, сейчас реализован как PHP-приложение (Apache,
Postgres, ~95 файлов / ~8300 строк в `public_html/`), без тестов и линтера
(см. CLAUDE.md исходного репозитория). Планируется переписать сайт на ASP.NET Core,
на первом этапе — максимально буквально ("1=1"), повторяя существующее поведение
без попытки сразу построить семантически идиоматичную архитектуру.

Поскольку у исходного приложения нет тестов, единственный способ быть уверенным,
что порт сохраняет поведение — сравнение с текущим PHP-приложением как источником
истины. Писать тесты сначала на PHP, а затем переписывать их на .NET нежелательно —
это двойная работа.

Отдельно стоял вопрос, где физически размещать код нового приложения и тесты:
в существующем PHP-репозитории или в новом.

## Решение

### 1. Тестовая стратегия: PHP-приложение как чёрный ящик

Текущий PHP-сайт уже собирается в Docker-образ и публикуется в `ghcr.io`
(CI/CD исходного репозитория). Это позволяет не трогать PHP-исходники вовсе:

- Тестовый проект на .NET (xUnit) поднимает PHP-приложение как чёрный ящик —
  через `docker compose` с готовым образом из `ghcr.io` и Postgres рядом
  (Testcontainers или аналог).
- Тесты пишутся один раз, **против PHP-версии**, как обычные интеграционные тесты
  (HTTP-запросы + проверка ответа / состояния БД). Зелёные тесты фиксируют текущее
  поведение как контракт.
- После написания ASP.NET Core реализации тот же тестовый проект прогоняется
  против неё — без переписывания тестов, только смена целевого сервера
  (base URL / фикстура запуска).

**Чтение** (GET-эндпоинты, списки игр, детали игры и т.д.):
тест делает запрос к серверу и проверяет тело/статус ответа обычными assert'ами.

**Запись** (добавление/редактирование/удаление игры, модерация и т.п.):
каждый тест поднимает БД в чистом, заранее засеянном состоянии (Testcontainers +
фикстура/seed на основе существующих `db-migrations/`), выполняет write-операцию
и проверяет **и** HTTP-ответ, **и** результирующее состояние затронутых таблиц —
это устраняет проблему общего мутируемого состояния при сравнении.

**Внешние интеграции** (email, VK, allrpg.info) не должны реально дёргаться в
тестах ни на PHP-, ни на .NET-стороне — их нужно застабить за одинаковым
интерфейсом/точкой подмены на обеих сторонах, чтобы тест проверял факт и
параметры вызова, а не реальную доставку.

Из ответов и состояния БД перед сравнением нормализуются недетерминированные поля:
автоинкрементные id, `now()`-таймстампы, CSRF-токены, session id.

### 2. Репозиторий: новый, отдельный от PHP-репозитория

Новый ASP.NET Core код и тестовый проект размещаются в **новом репозитории**,
а не как подпапка в существующем PHP-репозитории.

Схема БД (`db-migrations/*.sql` из PHP-репозитория) при необходимости копируется
в новый репозиторий по мере переноса каждого раздела функциональности — без
submodule, так как миграции меняются редко.

## Альтернативы и почему отклонены

- **Тесты на PHP → переписать на .NET** — двойная работа, отклонено сразу.
- **Ad-hoc differential-diff скрипт** (ручное сравнение сырых HTTP-ответов между
  двумя живыми инстансами вместо тестового фреймворка) — по сути та же идея, но
  без привычной инфраструктуры setup/teardown, ассертов и отчётности обычного
  тест-раннера. Обычные тесты (xUnit + Testcontainers), где PHP выступает как
  фикстура/оракул, дают тот же эффект удобнее и с меньшими накладными расходами.
- **Тот же репозиторий, подпапка `/dotnet`**: удобнее сверяться с оригиналом при
  портировании (код рядом) и не нужно синхронизировать миграции. Отклонено, так
  как усложняет CI (два стека в одном workflow), создаёт риск случайно задеть
  прод-пайплайн PHP-версии при экспериментах с .NET, и репозиторий надолго
  становится "и то, и то" на неопределённый срок миграции.

## Последствия

- Плюс: тесты переиспользуются полностью между эталонной и портируемой версией,
  без двойного написания.
- Плюс: новый репозиторий с чистой историей и независимым CI/CD, не рискует
  прод-пайплайном PHP-версии.
- Минус: схему БД придётся вручную синхронизировать между репозиториями по мере
  переноса разделов (компенсируется тем, что миграции меняются редко).
- Минус: при портировании потребуется держать открытым PHP-репозиторий отдельно,
  чтобы сверяться с исходным кодом (не в одном чекауте).
- Требование: внешние интеграции (email/VK/allrpg.info) должны быть спроектированы
  за подменяемым интерфейсом с первого дня работы над тестами, иначе write-тесты
  будет невозможно безопасно гонять.
