# Compat-тесты

Compat-тест — это тест, который сначала зеленеет на **PHP-оригинале**, фиксируя его поведение как
контракт, и только потом под него пишется код на .NET. Обоснование — [ADR 0001](adr001-repo-and-testing-strategy.md),
выбор фреймворка — [ADR 0002](adr002-test-stack.md).

Всё живёт в одном проекте: `src/KogdaIgra.CompatTests`.

## Как устроен харнесс

### `ISiteUnderTest`

`ISiteUnderTest.cs` — **единственная точка подмены цели**. Три члена: `BaseUrl`, `CreateClient()`,
`ResetDatabaseAsync()`. Сегодня реализация одна — PHP-оригинал; когда появится порт, добавится
вторая. Сами тесты про разницу знать не должны, поэтому обращаться напрямую к типу реализации в
теле теста нельзя (кроме `StartupFailure`, см. ниже).

### `PhpSiteUnderTest`

Поднимает PHP-версию как чёрный ящик, один раз на прогон:

1. создаёт docker-сеть (`NetworkBuilder`);
2. поднимает `postgres:15.18` (та же версия, что на проде PHP-версии) с алиасом `kogda-db` в этой
   сети — имя и креды повторяют `docker-compose.yml` PHP-репозитория;
3. поднимает контейнер сайта, пробрасывая `POSTGRES_*`, `SITENAME_HOST`, `SITENAME_SCHEME`.
   Порт на хосте выбирается **явно** (`FindFreePort`), а не случайным маппингом Testcontainers:
   PHP-приложению нужно знать свой публичный адрес (`SITENAME_HOST`) ещё до старта;
4. читает схему из образа сайта (`DatabaseSchema.ReadFromSiteAsync`), накатывает её и тестовые
   данные. Сайту БД до первого запроса не нужна, поэтому порядок именно такой;
5. ждёт не статус-код, а осмысленный HTML (`WaitUntilRespondsAsync`).

`MAILGUN_KEY` и `JOINRPG_CLIENT_ID`/`SECRET` намеренно не задаются: без них PHP-код сам становится
no-op на внешних интеграциях, и настоящие письма/OAuth-запросы из тестов не уходят (требование ADR 0001).

Если что-то не поднялось (нет Docker, недоступен образ), `InitializeAsync` записывает причину
в `StartupFailure`. Дальше всё зависит от того, где идёт прогон:

- **локально** исключение не бросается — тесты пропустятся с внятным сообщением, а не упадут пачкой
  невнятных ошибок. Так разработчик без Docker получает пропуски, а не красный прогон;
- **в CI** (задана переменная `CI`, GitHub Actions ставит `CI=true`) `InitializeAsync` бросает
  исключение, и TUnit роняет каждый тест, которому нужна фикстура. Иначе все тесты пропустились бы,
  и зелёная сборка не проверила бы ничего — так однажды и случилось, когда в образе не оказалось
  `/db-init`. Значение `CI=false` считается «не CI».

### `DatabaseSchema`

Читает все `*.sql` из `/db-init` образа сайта и накатывает их по порядку имён. Туда PHP-репозиторий
кладёт свой `db/init/` — снимок живой dev-базы (структура и справочники), см.
[db/README.md](../db/README.md). Схема и код всегда одной версии: они из одного образа.

Применяются они через `psql` **внутри контейнера**, а не через Npgsql: вывод `pg_dump` — это скрипт
для `psql`, а не чистый SQL, в нём есть мета-команды (\restrict) и блоки `COPY ... FROM stdin`.
Обычное соединение такое не выполнит.

`ResetAsync` делает `DROP SCHEMA public CASCADE` и накатывает всё заново — это состояние «чистой
засеянной базы» для write-тестов.

### `TestData`

Засевает `db/testdata/games.sql` поверх схемы и справочников и даёт тестам константы
(`TestData.Games.Active`, `TestData.ActiveGameName`, `TestData.CurrentYear`) вместо
магических чисел.

Данные **придуманы**, а не взяты из дампа: в реальных таблицах лежат адреса почты
организаторов. Набор подобран под то, как PHP отбирает игры: активная игра, удалённая
(`deleted_flag = 1`), ожидающая модерации (`-1`), игра со скрытой почтой, плюс
перенесённая дата (`order > 0`) у активной игры.

Две ловушки, на которых легко потерять полдня:

- В `_get_games` почти все связи — **INNER JOIN**, включая `ki_updates` через подзапрос
  `MAX(update_date)`. Игра без строки в `ki_updates` не появится **нигде**.
- Главная фильтрует по `date_part('year', begin) = $year`, где год берётся из PHP
  `date()` в зоне Europe/Moscow и **с ноября переключается на следующий**. Поэтому даты
  засеваются в `TestData.CurrentYear`, который повторяет это правило; тест на заголовок
  страницы заодно проверяет, что повторяет верно.

### `SiteResponse` — и главная готча

**PHP-приложение отвечает HTTP 200 даже когда БД сломана**: в теле тогда лежит сырой текст ошибки
Postgres. Это проверено экспериментально. Следствие: **ассерт, опирающийся только на статус-код,
не проверяет ничего.**

Поэтому есть `SiteResponse`:

- `ContainsDatabaseError(body)` — в теле вывалилась наружу ошибка Postgres;
- `LooksLikeHtmlPage(body)` — это похоже на настоящую страницу, а не на текст ошибки;
- `Parse(body)` — разбор через AngleSharp, для ассертов по структуре страницы;
- `Excerpt(body)` — короткая выжимка тела для сообщений об ошибках.

Каждый compat-тест, читающий страницу, обязан проверить отсутствие ошибки БД — иначе он останется
зелёным на полностью нерабочем сайте.

### Прочее

- `RepositoryLayout` — поиск корня репозитория (каталога с `KogdaIgra.slnx`) вверх от
  `AppContext.BaseDirectory`. Нужен потому, что из-за `UseArtifactsOutput` тесты запускаются из
  `artifacts/`, а не из папки проекта, и `db/` относительным путём не найти.
- `Normalization` — вычистка недетерминированных кусков из ответа перед сравнением. Пока там только
  `StripSessionId` (PHPSESSID). Наполняется по мере появления реальных тестов: сюда попадает только
  то, что действительно мешает сравнению, а не всё, что теоретически может отличаться.
- `SmokeTests` — проверка самого харнесса, а не сайта: поднимается ли PHP-оригинал и отдаёт ли
  осмысленную главную страницу с данными из засеянной БД.

## Как прогнать локально

Нужен только запущенный Docker:

```bash
dotnet test
```

Образ `ghcr.io/joinrpg/kogda-igra:latest` — **публичный**, анонимный `docker pull` работает,
логиниться в ghcr.io не нужно. Обратите внимание на владельца: пакет живёт в организации
`joinrpg`, а не `leotsarev` (форк в личном аккаунте образов не публикует).

### Прогон против локально собранного образа

Когда нужно проверить порт против ещё не опубликованных изменений PHP-версии, образ собирается
из соседнего чекаута:

```bash
cd ..\kogda-igra
docker compose build          # собирает образ kogda-igra-kogdaigra:latest
```

Сборка образа — единственное, что делается в PHP-репозитории. Ничего там не менять и не коммитить.

Затем из корня этого репозитория:

```bash
KOGDA_IGRA_IMAGE="kogda-igra-kogdaigra:latest" dotnet test
```

Имя переменной задаётся константой `PhpSiteUnderTest.ImageEnvironmentVariable`, значение по
умолчанию — `PhpSiteUnderTest.DefaultImageName`.

Если Docker не запущен или образ недоступен, тесты **пропустятся**, а не упадут: причина
попадает в `StartupFailure` и в сообщение о пропуске. Это только локально — в CI такой прогон
падает (см. `PhpSiteUnderTest` выше). Проверить падение локально можно, подставив образ без
`/db-init`:

```bash
KOGDA_IGRA_IMAGE=postgres:15.18 CI=true dotnet test -- --treenode-filter "/*/*/SmokeTests/*"
```

## Как добавить новый compat-тест

1. **Сначала выяснить, как ведёт себя PHP.** Поднять сайт (`docker compose up` в `..\kogda-igra`
   или прямо тестом) и посмотреть реальный ответ. Смотреть в исходники `..\kogda-igra\public_html`,
   чтобы понять, почему ответ такой.
2. Завести класс теста с фикстурой:

   ```csharp
   [ClassDataSource<PhpSiteUnderTest>(Shared = SharedType.PerTestSession)]
   public class GameListTests(PhpSiteUnderTest site)
   ```

3. Первой строкой каждого теста — пропуск, если сайт не поднялся (сработает только локально,
   в CI тест до этой строки не дойдёт):

   ```csharp
   Skip.When(site.StartupFailure is not null, $"PHP-сайт не поднялся: {site.StartupFailure}");
   ```

4. Запрос через `site.CreateClient()`, проверка тела через `SiteResponse`. Статус-коду не верить.
5. Для write-теста — `await site.ResetDatabaseAsync()` в начале, дальше проверять **и** HTTP-ответ,
   **и** состояние затронутых таблиц (Npgsql).
6. Прогнать против PHP. Тест должен позеленеть **до** того, как под него написан код на .NET.

Если тест невозможно прогнать против PHP — остановиться и подумать. Это либо тест не про то, либо
харнессу не хватает возможности, которую надо добавить.

## Переключение на .NET-реализацию

Когда появится порт:

1. Добавить `AspNetSiteUnderTest : ISiteUnderTest` — поднимает портал (`WebApplicationFactory` либо
   свой контейнер) и тот же `postgres:15.18` со схемой из `/db-init` образа PHP-версии.
2. Переключить `[ClassDataSource<...>]` на новую фикстуру — тесты не переписываются.
3. На время миграции разумно уметь гонять оба набора: PHP-прогон остаётся оракулом, пока раздел не
   портирован полностью.

Для этого тесты и не должны зависеть ни от чего PHP-специфичного, кроме `StartupFailure`. Всё
PHP-специфичное (имена переменных окружения контейнера, ожидание старта, выбор порта) живёт внутри
`PhpSiteUnderTest`.

## Внешние вызовы

Приложение ходит наружу в трёх местах: почта через Mailgun, вход через OAuth JoinRPG
и обновление лайков из ВКонтакте. Первые два глушатся сами — без ключей в окружении
код выходит из функции первой же строкой. А вот VK дёргается **без всяких ключей**.

Поэтому харнесс уводит внешние хосты в никуда: `api.vkontakte.ru`, `api.eu.mailgun.net`,
`id.joinrpg.ru` и `devid.joinrpg.ru` указывают на `127.0.0.1` внутри контейнера
(`WithExtraHost` в `PhpSiteUnderTest`). Там на 443 никто не слушает, соединение
отвергается сразу, без ожидания таймаута.

Без этого тест эндпоинта лайков стучался бы в настоящий VK — с машины разработчика
и из CI.

Для VK этого достаточно: там проверяется поведение при недоступности, и оно оказалось
разрушительным — см. [#77](https://github.com/joinrpg/kogda-igra/issues/77). Подменить
сам ответ VK нельзя: адрес зашит в код, а вызов идёт по HTTPS.

### Вход через JoinRPG — подменяется целиком

С OAuth повезло: адрес сервера берётся из `JOINRPG_ID_BASE`, а идентификатор и секрет
клиента — из `JOINRPG_CLIENT_ID` и `JOINRPG_CLIENT_SECRET`. Значит сервер можно увести
на **обычный HTTP**, и сертификат не нужен вовсе.

Харнесс поднимает поддельный сервер (`oidc-mock/`) в той же сети под именем
`joinrpg-id` и указывает на него приложение. Сервер отвечает на `/connect/token`
и `/connect/user_info`, а каждый полученный запрос дописывает в журнал, который тест
читает через `site.IdentityProviderRequests`. Так проверяется не только результат
входа, но и **что именно приложение отправило**: `code_verifier` из PKCE, секрет
клиента, совпадение `redirect_uri` с первым шагом.

Адрес почты кодируется прямо в authorization code, поэтому тест управляет исходом,
не договариваясь с сервером отдельно. Особые значения `deny-token` и `deny-email`
изображают отказ на каждом из двух шагов обмена.

Грабли: Apache **не пробрасывает заголовок `Authorization`** в PHP. Без строки
`RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]` в `.htaccess`
поддельный `user_info` не видит токен, вход молча не срабатывает, и выглядит это
как ошибка приложения.

## Write-тесты

По ADR 0001 write-тест проверяет **и** HTTP-ответ, **и** состояние затронутых таблиц.
Для второго есть `Database.CountAsync` / `Database.ScalarAsync` поверх
`site.ConnectionString`.

Перед каждым таким тестом база возвращается в исходное состояние вызовом
`site.ResetDatabaseAsync()` — это `DROP SCHEMA public CASCADE` плюс повторное применение
схемы, справочников и фикстур.

Хук помечен **и** `[Before(HookType.Test)]`, **и** `[After(HookType.Test)]`. «До» —
чтобы тест не зависел от соседей, «после» — чтобы соседи не зависели от него. Без
второго последний write-тест оставлял бы за собой переименованную или удалённую игру,
и падали бы уже read-тесты, идущие следом: прогон последовательный, так что порядок
имеет значение.

Ещё одна ловушка: POST надо слать на `/edit/game/` — **со слэшем**. `/edit/game` это
каталог, Apache отвечает на него 301, а при переходе по редиректу POST вырождается
в GET и тело теряется. Правка при этом молча не применяется, тест падает на ассерте
по БД, а причина выглядит как «PHP не сохраняет».

Из-за этого **весь набор гоняется последовательно**: `[assembly: NotInParallel]` в
`AssemblyAttributes.cs`. Сайт и БД одни на весь прогон, и если read-тест сделает запрос
в момент пересоздания схемы, он упадёт с необъяснимой ошибкой. Пометки `[NotInParallel]`
на одном классе для этого недостаточно — она разводит только те тесты, что её несут.

Внешние интеграции при этом молчат сами: в окружении контейнера нет `MAILGUN_KEY`,
и `Email::mg_send` выходит из функции первой же строкой. Подменять типы не требуется —
и не разрешается, моки в этом репозитории запрещены.

## Вход под пользователем

Раздел `/edit/` доступен только с правом `EDIT_GAMES`, а вход в PHP-версии идёт через
OAuth JoinRPG — в тестах он заглушён отсутствием ключей, и пройти его негде.

Обходится без единой правки PHP: авторизация опирается только на `$_SESSION['user_id']`
(`appcode/user_funcs.php`), а сессии этот образ хранит файлами в `/tmp`. Харнесс кладёт
в контейнер готовый файл `/tmp/sess_<id>` с содержимым `user_id|i:<uid>;` и присылает
cookie `PHPSESSID` — `site.CreateLoggedInClientAsync(userId)`.

Важная деталь: файл создаётся от root, а Apache работает под `www-data`. Без права на
запись PHP не сможет обновить сессию и **молча начнёт новую** — тест будет выглядеть
как «вход не сработал». Поэтому файл кладётся с режимом `rw-rw-rw-`.

Права выдаются засевом `users` + `user_privs` (`pid = 4` — это `EDIT_GAMES`).

## Изменения схемы в PHP-версии

Здесь делать ничего не нужно. Схема живёт в `db/init/` PHP-репозитория и приезжает в тесты
вместе с образом: как только новый образ опубликован (или подставлен через `KOGDA_IGRA_IMAGE`),
тесты гоняются на его схеме. Подробности — в [db/README.md](../db/README.md).

## Compat-тесты в CI

Образ публичный, поэтому GitHub Actions тянет его анонимно — никаких секретов и `docker login`
не требуется. Docker на `ubuntu-24.04` доступен из коробки, Testcontainers работает.

Если сайт в CI не поднимется (недоступен реестр, убрали тег, в образе чего-то не хватает), тесты
не пропустятся, а упадут и свалят сборку — см. `PhpSiteUnderTest` выше. Сводку прогона TUnit пишет
в summary job'а, HTML-отчёт лежит в артефакте `test-results`.
