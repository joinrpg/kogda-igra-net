# Compat-тесты

Compat-тест — это тест, который сначала зеленеет на **PHP-оригинале**, фиксируя его поведение как
контракт, и только потом под него пишется код на .NET. Обоснование — [ADR 0001](adr001-repo-and-testing-strategy.md),
выбор фреймворка — [ADR 0002](adr002-test-stack.md).

Всё живёт в одном проекте: `src/KogdaIgra.CompatTests`.

## Как устроен харнесс

### `ISiteUnderTest`

`ISiteUnderTest.cs` — **единственная точка подмены цели**. Три члена: `BaseUrl`, `CreateClient()`,
`ResetDatabaseAsync()`. Сегодня реализация одна — PHP-оригинал; когда появится порт, добавится
вторая. Сами тесты про разницу знать не должны, поэтому обращаться напрямую к типу реализации в
теле теста нельзя (кроме `StartupFailure`, см. ниже).

### `PhpSiteUnderTest`

Поднимает PHP-версию как чёрный ящик, один раз на прогон:

1. создаёт docker-сеть (`NetworkBuilder`);
2. поднимает `postgres:14.2` (та же версия, что на проде PHP-версии) с алиасом `kogda-db` в этой
   сети — имя и креды повторяют `docker-compose.yml` PHP-репозитория;
3. накатывает схему через `DatabaseSchema.ApplyAsync`;
4. поднимает контейнер сайта, пробрасывая `POSTGRES_*`, `SITENAME_HOST`, `SITENAME_SCHEME`.
   Порт на хосте выбирается **явно** (`FindFreePort`), а не случайным маппингом Testcontainers:
   PHP-приложению нужно знать свой публичный адрес (`SITENAME_HOST`) ещё до старта;
5. ждёт не статус-код, а осмысленный HTML (`WaitUntilRespondsAsync`).

`MAILGUN_KEY` и `JOINRPG_CLIENT_ID`/`SECRET` намеренно не задаются: без них PHP-код сам становится
no-op на внешних интеграциях, и настоящие письма/OAuth-запросы из тестов не уходят (требование ADR 0001).

Если что-то не поднялось (нет Docker, недоступен образ), `InitializeAsync` не бросает исключение, а
записывает причину в `StartupFailure` — чтобы тесты пропустились с внятным сообщением, а не упали
пачкой невнятных ошибок.

### `DatabaseSchema`

Накатывает `db/schema/schema.sql`, затем `db/migrations/*.sql` в алфавитном порядке — ровно так же,
как это происходит на живой базе PHP-версии. `ResetAsync` делает `DROP SCHEMA public CASCADE` и
накатывает всё заново — это состояние «чистой засеянной базы» для write-тестов.

### `SiteResponse` — и главная готча

**PHP-приложение отвечает HTTP 200 даже когда БД сломана**: в теле тогда лежит сырой текст ошибки
Postgres. Это проверено экспериментально. Следствие: **ассерт, опирающийся только на статус-код,
не проверяет ничего.**

Поэтому есть `SiteResponse`:

- `ContainsDatabaseError(body)` — в теле вывалилась наружу ошибка Postgres;
- `LooksLikeHtmlPage(body)` — это похоже на настоящую страницу, а не на текст ошибки;
- `Parse(body)` — разбор через AngleSharp, для ассертов по структуре страницы;
- `Excerpt(body)` — короткая выжимка тела для сообщений об ошибках.

Каждый compat-тест, читающий страницу, обязан проверить отсутствие ошибки БД — иначе он останется
зелёным на полностью нерабочем сайте.

### Прочее

- `RepositoryLayout` — поиск корня репозитория (каталога с `KogdaIgra.slnx`) вверх от
  `AppContext.BaseDirectory`. Нужен потому, что из-за `UseArtifactsOutput` тесты запускаются из
  `artifacts/`, а не из папки проекта, и `db/` относительным путём не найти.
- `Normalization` — вычистка недетерминированных кусков из ответа перед сравнением. Пока там только
  `StripSessionId` (PHPSESSID). Наполняется по мере появления реальных тестов: сюда попадает только
  то, что действительно мешает сравнению, а не всё, что теоретически может отличаться.
- `SmokeTests` — проверка самого харнесса, а не сайта: поднимается ли PHP-оригинал и отдаёт ли
  осмысленную главную страницу с данными из засеянной БД.

## Как прогнать локально

Нужен запущенный Docker.

Образ `ghcr.io/leotsarev/kogda-igra` — **приватный**, и тег `latest` у него ставится только релизам,
так что `docker pull ghcr.io/leotsarev/kogda-igra:latest` сейчас падает с «not found». Поэтому образ
собирается локально из соседнего чекаута PHP-репозитория:

```bash
cd ..\kogda-igra
docker compose build          # собирает образ kogda-igra-kogdaigra:latest
```

Сборка образа — единственное, что делается в PHP-репозитории. Ничего там не менять и не коммитить.

Затем из корня этого репозитория:

```bash
KOGDA_IGRA_IMAGE="kogda-igra-kogdaigra:latest" dotnet test
```

Проверено: 2 теста проходят. Без `KOGDA_IGRA_IMAGE` харнесс попробует приватный образ из ghcr.io,
не сможет его получить и тесты **пропустятся** (не упадут) с причиной в сообщении.

Имя переменной задаётся константой `PhpSiteUnderTest.ImageEnvironmentVariable`.

## Как добавить новый compat-тест

1. **Сначала выяснить, как ведёт себя PHP.** Поднять сайт (`docker compose up` в `..\kogda-igra`
   или прямо тестом) и посмотреть реальный ответ. Смотреть в исходники `..\kogda-igra\public_html`,
   чтобы понять, почему ответ такой.
2. Завести класс теста с фикстурой:

   ```csharp
   [ClassDataSource<PhpSiteUnderTest>(Shared = SharedType.PerTestSession)]
   public class GameListTests(PhpSiteUnderTest site)
   ```

3. Первой строкой каждого теста — пропуск, если сайт не поднялся:

   ```csharp
   Skip.When(site.StartupFailure is not null, $"PHP-сайт не поднялся: {site.StartupFailure}");
   ```

4. Запрос через `site.CreateClient()`, проверка тела через `SiteResponse`. Статус-коду не верить.
5. Для write-теста — `await site.ResetDatabaseAsync()` в начале, дальше проверять **и** HTTP-ответ,
   **и** состояние затронутых таблиц (Npgsql).
6. Прогнать против PHP. Тест должен позеленеть **до** того, как под него написан код на .NET.

Если тест невозможно прогнать против PHP — остановиться и подумать. Это либо тест не про то, либо
харнессу не хватает возможности, которую надо добавить.

## Переключение на .NET-реализацию

Когда появится порт:

1. Добавить `AspNetSiteUnderTest : ISiteUnderTest` — поднимает портал (`WebApplicationFactory` либо
   свой контейнер) и тот же `postgres:14.2` со схемой из `db/`.
2. Переключить `[ClassDataSource<...>]` на новую фикстуру — тесты не переписываются.
3. На время миграции разумно уметь гонять оба набора: PHP-прогон остаётся оракулом, пока раздел не
   портирован полностью.

Для этого тесты и не должны зависеть ни от чего PHP-специфичного, кроме `StartupFailure`. Всё
PHP-специфичное (имена переменных окружения контейнера, ожидание старта, выбор порта) живёт внутри
`PhpSiteUnderTest`.

## Обновление `db/` из PHP-репозитория

Когда в PHP-репозитории появляется новая миграция в `db-migrations/` — скопировать файл **как есть**
в `db/migrations/`. Имена файлов определяют порядок применения (сортировка по имени, ordinal).
Подробности и правила конвертации схемы — в [db/README.md](../db/README.md).

## TODO: compat-тесты в CI

**Сейчас в CI compat-тесты фактически не выполняются — они пропускаются.**

`GITHUB_TOKEN` этого репозитория не имеет доступа к пакету, опубликованному в другом репозитории,
поэтому workflow не может выполнить `docker pull ghcr.io/leotsarev/kogda-igra`. Харнесс обрабатывает
это штатно: контейнер не поднимается, `StartupFailure` заполняется, тесты помечаются пропущенными.
Билд зелёный, но проверки не было.

Варианты решения (нужно решение владельца репозитория):

- PAT с правами `read:packages` в секретах этого репозитория + `docker login ghcr.io` в workflow;
- сделать пакет публичным;
- собирать образ в CI из checkout PHP-репозитория (нужен доступ на чтение к приватному репозиторию,
  то есть снова PAT).

До принятия решения зелёный CI **не означает**, что compat-тесты прошли. Перед мержем прогонять их
локально.
