# Схема БД

## Откуда берётся

**Схема живёт в PHP-репозитории**, а не здесь: `db/init/01-schema.sql` (структура) и
`db/init/02-reference-data.sql` (справочники). Это снимок живой dev-базы; dev и prod — две базы на
одном сервере PostgreSQL 15.18, так что он отражает и структуру прода. Подробности, включая как
его переснять, — в `db/README.md` PHP-репозитория.

PHP-репозиторий кладёт `db/init/` в Docker-образ сайта каталогом `/db-init`. Тесты читают схему
**из того же образа, против которого гоняются** (`DatabaseSchema.ReadFromSiteAsync`). Поэтому
версия схемы всегда совпадает с версией кода — и для опубликованного `ghcr.io/joinrpg/kogda-igra:latest`,
и для образа, подменённого через `KOGDA_IGRA_IMAGE`. Копировать что-либо из PHP-репозитория
сюда не нужно.

Образ, собранный до переезда схемы, `/db-init` не содержит — тогда тесты пропускаются с
сообщением об этом.

| Каталог | Что внутри |
|---|---|
| `testdata/` | Придуманные тестовые данные поверх схемы, см. `TestData` |
| `local/snapshot.sql` | Полный дамп dev с данными — только `utils/fetch-dev-db.ps1` |

`db/local/` **заигнорен и не коммитится**: в `users` и `ki_games` лежат адреса электронной
почты, причём у игр есть флаг `hide_email`. Эти данные не должны попадать в репозиторий.

## Почему снимок, а не миграции

Раньше здесь лежала схема, переведённая вручную из MySQL-дампов 2012 года
(`mysql-db-structure/*.sql` в PHP-репозитории), плюс каталог `db/migrations/` с
инкрементальными миграциями. От этого отказались: снимок живой базы всегда точен, а дампы
2012 года требовали ручной конвертации диалекта и отставали на все миграции.

## Кодировка: почему pg_dump пишет в примонтированный каталог

`pg_dump` запускается с `--file` в примонтированный каталог, а **не** через конвейер
PowerShell. Это не стилистика: PowerShell декодирует вывод нативной команды кодировкой
консоли (`[Console]::OutputEncoding`). На консоли с CP866 — а это обычная ситуация на
русской Windows — UTF-8 из контейнера читается как CP866, и вся кириллица превращается
в псевдографику (`Все игры` → `╨Т╤Б╨╡ ╨╕╨│╤А╤Л`).

Порча обратима (`.encode('cp866').decode('utf-8')`), но полагаться на это не надо.
В скрипте есть проверка: если в результате встречается псевдографика, он падает.

## Как применяется в тестах

`DatabaseSchema` читает все `*.sql` из `/db-init` контейнера сайта, копирует их в контейнер
Postgres и выполняет через `psql` в порядке имён — так же, как это делает
`docker-entrypoint-initdb.d`. Через `psql`, а не через Npgsql, — принципиально: вывод `pg_dump` —
скрипт для `psql`, а не чистый SQL. В нём есть мета-команды (`\restrict`, `\unrestrict`) и блоки
`COPY ... FROM stdin` с терминатором `\.`, которые обычное соединение выполнить не может.

Поэтому схема накатывается **после** старта контейнера сайта. Самому сайту БД до первого
запроса не нужна.
